# Коллаборация в FlexCrm и запись агента в живой документ

Спецификация охватывает подключение коммерческого модуля к базовому редактору и один будущий адаптер AI для живого текста. Целевая установка — закрытая облачная FlexCrm. FlexCms сохраняет одиночное редактирование через существующий REST API. Протокол книг выбирается в пакете таблиц. Предлагаемый адаптер относится к документам Tiptap с Yjs.

## Переход из одиночного документа в живую комнату

У исходного `DocumentStateWriter` новый rich text получает `collab_protocol` по возможностям типа ещё при создании. Даже одиночный autosave в этой реализации меняет epoch при заполненном protocol. Для целевой схемы `v_documents.write_mode` фиксирует, кто сейчас владеет записью. Новый документ имеет `snapshot`; обычные сохранения меняют позицию, а поколение остаётся прежним. Когда авторизованный владелец активирует журнал, он под блокировкой и после проверки политики атомарно повышает epoch и state_version и фиксирует `journal`. Токен содержит новое поколение. Повторно открывающий эту комнату читатель получает read-only сессию. Читатель, открывающий одиночный документ, получает его обычное представление, без побочной смены владельца или версии.

В journal любой старый autosave по HTTP блокируется у владельца, даже если Hub не отвечает. Управляемый возврат в snapshot требует остановить ввод, зафиксировать непрерывный журнал и checkpoint, повысить epoch и state_version. Restore также всегда меняет поколение. Дубликаты очереди, offline envelope, запоздалые bytes, токен старого поколения и ранее выданная аренда проверяются под блокировкой поколения. В 3.5 при обработке изменений в строгой комнате проверяется также аренда её писателя. Прежнее владение после восстановления комнаты не возобновляется по одному факту переподключения. 3. Протокол 2 даёт возможность отправлять изменения при достаточных правах. Hub сверяет токен с живой политикой PHP и при необходимости оставляет комнату доступной только для чтения. Зритель, устаревшая схема, отзыв прав, истёкшая сессия, окончание поколения и временная недоступность сервера имеют собственные исходы. Сетевая недоступность при известном результате и неизвестный исход после потери ответа требуют разных повторов. [Автомат статусов Vue](../../packages/vue-collaboration/src/status.ts)

### Как checkpoint сохраняет параллельный ввод

В 2.x компактор читает бинарную основу на позиции C и непрерывный хвост по H под блокировкой документа и головы. PHP записывает в голову токен, держателя, срок и `lease_through_seq=H` в той же транзакции. При публикации PHP заново блокирует документ и голову. Для текущего journal, поколения, привязки, версии checkpoint и действующего токена принимает только `covered_from=C` и `C ≤ covered_through ≤ lease_through_seq`. Время сравнивается после захвата блокировок по часам БД, срок в `lease_expires_at` хранится в UTC. Сохранение бинарной основы и проекции, продвижение checkpoint, удаление покрытых payload и погашение lease выполняются одной транзакцией. Pending снимается только для покрытой позиции своего поколения.

Рабочий Hub помечает результат верхней позицией реально полученной выборки. Исходный PHP проверяет верхнюю границу по текущей голове. Если после выдачи до 41 приняли обновление 42, ошибочно помеченный как 42 checkpoint со старой выборкой удовлетворяет исходному условию. Новый предел отклоняет такое сообщение. Публикация до 41 сохраняет байты и маркер 42. Перед выключением journal проверку равенства checkpoint и головы повторяют под теми же блокировками, что и append. [Исходная проверка диапазона](../../packages/collaboration/src/Persistence/Checkpoint.php) · [Сборка checkpoint в Hub](../../packages/collaboration/hub/src/compaction.js) · [SQL-проверка границы](../checks/collaboration/lease-schema.sql)

## Почему нужен отдельный путь для команд агента

Уже сегодня `UpdateLog::append` блокирует состояние документа и голову нужного поколения, сверяет идентификатор бинарного обновления с его хешем и одним commit записывает байты, квитанцию, новую позицию головы и маркер отставания проекции. В Hub `handleEnvelope` применяет обновление в памяти перед постановкой в очередь сохранения. Существующий `serverWrite` также меняет живой Y.Doc, затем в durable-режиме ожидает подтверждения. Поэтому другая вкладка уже может видеть «20», пока подготовка агента из PostgreSQL ещё читает «15». Ожидание ACK в режиме `durable` происходит позже этого окна. [Текущий Hub](../../packages/collaboration/hub/src/persistence.js) · [Журнал владельца](../../packages/collaboration/src/Persistence/UpdateLog.php)

Для агента исход команды A42, состоящей из замены и вставки, должен быть полностью определён относительно проверенного фрагмента. Она может пережить падение между commit и ответом, а затем дать доказуемый исход. Повтор вызова `serverWrite` может сгенерировать новые байты и повторно вставить абзац. `Y.Doc.transact` группирует изменения, но исключение после первой операции само по себе не возвращает Y.Doc в исходное состояние. [Порядок событий и аварийные сценарии A42](../examples/live-write.json)

## Предлагаемый протокол для одного документа

Для 3.5 выбран строгий протокол A. Браузерные и агентские изменения сначала фиксируются в журнале PostgreSQL, затем Hub применяет их и публикует клиентам. Команда агента готовится на одноразовой копии подтверждённого состояния. Первый профиль использует одного активного писателя на документ и поколение без штатного Redis-расширения (multi-instance масштабирование строится через L7 sticky-маршрутизацию по `hash(document_id)` + PG lease `(owner_id, owner_fence)` с TTL `15 s` по `clock_timestamp()` + Redis **Control-Only** Pub/Sub для сигналов `wakeup`, `revoke_subject`, `epoch_bump_4409`, `handoff_request` и close code **`4412` Lease Handoff**). Целевые версии Hub и Yjs: **`@hocuspocus/server >= 4.9.0`** (фиксы `#1123` очереди `beforeHandleMessage`, `#1155/#1157/#1163/#1174`, `#1206` блокировки рассылки до загрузки, батчинг `flushDelay: 80ms`) и **`yjs >= 13.6.33` / `lib0 >= 0.2.119`** (фикс расхождения `#823`). **На серверном `Y.Doc` категорически запрещено инстанцировать `Y.UndoManager`** (баг `yjs#833`). [Lockfile Hub](../../packages/collaboration/hub/package-lock.json) · [SLO-бюджеты](engineering-standards.md#38-slo-бюджеты-производительности-и-opentelemetry-2026)

Строгий профиль закрепляется за поколением у владельца. Действующая комната переходит в него после остановки ввода, закрытия прежнего поколения и открытия нового с подтверждённой бинарной основой. Сессии строгого поколения обслуживает только совместимая сборка Hub. Закрытие старых соединений и проверка профиля при загрузке нужны до выдачи новой сессии, чтобы старый Hub не мог показать чужим клиентам правку даже при отказе append в PHP.

Офисный SDK владеет командой пользователя. Владелец документа ведёт авторитетный исход её записи и корреляцию с журналом. В установке с общей PostgreSQL используется одна физическая транзакция для принятого обновления, связи с командой, квитанции и записи outbox. При разделении сервисов агент хранит локальную копию статуса и сверяет её с квитанцией владельца. Коммит в двух независимых БД не даёт того же свойства.

| Значение | Владелец и область |
| --- | --- |
| `command_id` | Хост создаёт до вызова commit. Ключ уникален по (tenant_id, project_scope, effective_subject, resource_id, command_id). В фикстуре этим полям соответствуют организация school-7, проект legal, инициатор user-9, contract-17 и A42. Токен и квитанция имеют ту же доверенную область. Поколение, намерение, версия схемы и предусловия входят в неизменяемое тело. Сервер вычисляет его отпечаток. Повтор с другим телом даёт конфликт ключа |
| `generation`, `head_seq` | Поколение и последняя принятая позиция авторитетного журнала документа. Restore открывает новое поколение. Нумерация позиций имеет смысл только в пределах поколения |
| `applied_seq` | Непрерывный префикс журнала, реально воспроизведённый данным экземпляром комнаты. Догоняющая комната временно может отставать от `head_seq` |
| `update_id`, хеш, байты | Идентичность физического обновления в протоколе Yjs. Одной подтверждённой команде соответствует сохранённая последовательность точных байтов и позиций. Границы команды сохраняются даже при нескольких обновлениях |
| `receipt_id`, `marker` | Неизменяемый результат фиксации команды с указанием документа, `generation` и `position`. Для проверяемых целей сохраняются компактные постусловия и способ прочитать соответствующую историческую редакцию |
| Владение комнатой | На время подготовки и применения есть один активный писатель. При смене владельца монотонный номер владения позволяет PHP отклонить завершение устаревшего процесса. Долгую подготовку Node выполняет вне SQL-транзакции |

Эффективная `text.replace_exact@1` и составная A42 в первом профиле упаковываются каждая в одно бинарное обновление. No-op фиксирует исход на текущей позиции без новой записи обновления. Внутренний журнал сохраняет диапазон позиций для владельцев, которым позднее понадобится несколько обновлений на команду.

**Владение записью в 3.5.** PHP выдаёт новую аренду процессу Hub в открытом journal текущего поколения под блокировками документа и головы. Для свободной либо истёкшей аренды увеличивает `owner_fence`, даже если тот же процесс предъявил свой прежний ID. Продлевать аренду может только пара `(owner_id, owner_fence)` с ещё действующим сроком. Время получения блокировки и последующей проверки берётся из `clock_timestamp()` базы. Значение `now()` в PostgreSQL относится к началу транзакции и может устареть во время ожидания. При освобождении обнуляют holder и срок под той же проверкой пары, сохраняя номер fence. В строгой комнате обладающий правом пользователь передаёт ввод активному Hub. PHP отвергает append, no-op и terminal reject от прежнего владельца даже при совпавшем head_seq. Все процессы, принимающие записи этой комнаты, должны применять данный контракт перед включением возможности. Пакет Collaboration 2.x обслуживает обычных редакторов без командного журнала или AI.

Аренда компактора разрешает собрать checkpoint из уже принятых байтов. В 3.5 смена писателя комнаты сама по себе оставляет выданный компактору префикс достоверным. Публикацию по этому префиксу проверяют по его собственным токену, сроку, границам и версии. Restore, закрытие поколения или замена lease исключают старую публикацию.

**Приём намерения.** По доверенному контексту PHP устанавливает субъект и проверяет доступ. В первой короткой транзакции сохраняет или находит намерение. Совпадающий ключ и отпечаток дают уже известный статус. Работа может продолжиться после исчезновения первоначальной Laravel job. После фиксации намерения `office.status` выдаёт `running`. При возврате статуса повторно проверяются субъект, область и актуальные права. Согласие рецензента хранится отдельно и позволяет выполнить только предложение с указанным digest от имени исходного инициатора.

**Браузерный и серверный ввод.** Строгая комната открывает соединения Hocuspocus в read-only на уровне транспорта. Протокол Vaulter принимает envelope через `onStateless` с отдельной проверкой пользовательского Edit в PHP. Штатные sync step 2 и update не меняют комнату. Очередь `beforeHandleMessage` в Hocuspocus 4.3.0 принадлежит соединению, а `DirectConnection.transact` и штатный Redis могут менять комнату без неё. Все разрешённые писатели используют обработчик комнаты и fenced append. До append обработчик применяет новый envelope к копии подтверждённой основы. При недостающих причинных зависимостях клиент сохраняет его для повтора, а журнал и комната остаются на прежней позиции. PHP проверяет позицию основы под блокировкой и отклоняет legacy append без fence в строгом поколении. Синхронизация второго клиента и ACK первого следуют за фиксацией. Первый клиент может раньше показать собственный неподтверждённый ввод. [Точки интеграции](implementation/vaulter.md#35-запись-в-живой-текст) · [Стенд путей Hocuspocus](../examples/reference/live-write/hocuspocus-paths.mjs)

При неизвестном исходе append браузер повторяет исходный envelope, пока действует его поколение. Владелец сверяет ID и хеш с квитанцией обновления. Для совпавшего повтора Hub догоняет сохранённую позицию и отвечает тем же ACK. Изменённые байты под прежним ID отклоняются.

**Подготовка.** Для команды берётся одна согласованная выборка владельца с `generation`, бинарным checkpoint и непрерывным хвостом до `base_seq`. Проверяются позиции, хеши и полнота применения. Дыры в SQL-позициях и оставшиеся после загрузки `pendingStructs` или `pendingDs` в Yjs останавливают подготовку и продвижение позиции. Из бинарной основы сохраняются CRDT-идентификаторы. На копии требуется ровно одно совпадение `attrs.blockId` из 3.1 и совпадение смыслового контекста, текста и marks с атрибутами. После точечной правки проверяются схема ProseMirror и постусловия. Те же байты должны воспроизвести результат на свежей копии той же основы. При исключении уничтожается вся временная копия. Закрытый браузер и отсутствие загруженной комнаты допускают подготовку из того же журнала. [Исходники Yjs 13.6.31](https://github.com/yjs/yjs/blob/v13.6.31/src/utils/encoding.js)

Отсутствие Yjs `clientID` в уже загруженной истории ещё не исключает совпадение с несохранённым вводом офлайн-вкладки (на 32-битном пространстве вероятность коллизии достигает 1.16% при 10 000 сессий). В строгом профиле пространство `clientID` жёстко делится по границе **`2^31` (`0x80000000`)**: `[1 .. 2 147 483 647]` выделяются исключительно для серверных мутаций и AI-агентов (монотонно в `v_collaboration_client_ids`), а `[2 147 483 648 .. 4 294 967 295]` — для пишущих браузерных/офлайн-вкладок. Hub привязывает выданный `boundClientId` к соединению и через `Y.decodeUpdate` / `Y.decodeUpdateV2` до SQL append за O(1) отклоняет любые клиентские структуры с `item.id.client < 0x80000000` или `!== conn.boundClientId`, проверяет отсутствие `pendingStructs`/`pendingDs`, а чистые удаления детектирует сравнением полных V2-снимков (`structs + DeleteSet`). Пороги compaction: `>= 200` дельт, `>= 256 КБ` хвоста, простой `>= 60 с` или выгрузка комнаты (вызов `Y.encodeStateAsUpdateV2` выносится из мьютекса на клоне состояния; `gc: true` в активной комнате). Клиентский `Y.UndoManager`: `captureTimeout: 500`, глубина стека `<= 100`. Стенд принудительно подаёт поддельный `clientID = 100` (`< 2^31`) и совпадение с офлайн-вкладкой, проверяя отказ до продвижения позиции.

**Фиксация.** Во второй короткой транзакции PHP следует порядку блокировок Vaulter, повторно проверяет доступ, `write_mode`, схему, поколение, действующий fence и равенство `head_seq = base_seq`. Транзакция пишет точные байты, новую голову и маркер отставания, связывает обновления с намерением, фиксирует исход и событие доставки. Подготовка в Node проходит вне транзакции, поэтому между чтением основы и фиксацией может пройти браузерный append. При смене только позиции обработчик отбрасывает результат старой подготовки, дочитывает журнал и заново проверяет предусловия с тем же ключом. Проверка равенства позиции нужна также для no-op и отказа, вычисленного на копии. На неизменившейся актуальной основе изменение цели фиксирует `rejected` с `precondition_failed` без записи обновления. Число повторов в одной попытке ограничено. При исчерпании попытки временный исход оставляет `running` для последующей обработки. Повтор завершённой команды возвращает сохранённый исход с актуальной проверкой прав.

**Доставка.** `committed` доступен сразу после SQL commit, в том числе при отсутствии браузеров или падении Hub. Outbox будит открытую комнату по `(resource_id, generation, position)`. Она догоняет журнал и применяет точные сохранённые байты с собственным origin Hub, который `capture()` исключает из повторной записи. Дубликат сверяется с журналом, пропуск позиции запускает догон, событие другого поколения отбрасывается. При недоступности открытой комнаты доставка повторяется, поэтому после восстановления клиент может увидеть сохранённый результат без нового ввода. Закрытую комнату можно загрузить позднее из checkpoint и хвоста. Для следующей записи или чтения с заданной нижней границей нужен подтверждённый непрерывный префикс. При отставании, которое уже покрыто компакцией, Hub загружает свежий бинарный checkpoint и хвост. Фоновое задание после тайм-аута опрашивает `office.status` по исходному ключу. Квитанция отражает факт записи, а прогресс доставки относится к экземпляру комнаты.

**Проверка результата.** `office.verify(at_commit)` читает состояние на позиции квитанции или сохранённое доказательство этих постусловий. Компакция может удалить исходные байты из хвоста, поэтому доказательство и квитанция удерживаются по своим срокам. `office.read` с `after_receipt` и `office.verify(current)` используют подтверждённый префикс того же поколения на позиции как минимум из квитанции. State vector не подтверждает эту границу, поскольку чистое удаление может оставить его прежним. При отстающей проекции разрешённое адресное чтение восстанавливается из бинарной основы и хвоста либо возвращает `projection_pending`. После restore эти текущие операции возвращают `generation_changed`. Поздняя правка офлайн-вкладки может исказить смысл уже сохранённой операции. Evidence хранит относительные позиции Yjs вокруг каждого заменённого участка с одним соседним символом по краям, и `current` сверяет это окно. Результат `failed` сообщает о расхождении с текущим текстом, а сохранённый исход остаётся доступен для `at_commit` при текущем праве на историю. [Контракт SDK](agent-sdk.md#команды-содержимого)

## Приёмка и условия включения

[Машиночитаемый сценарий A42](../examples/live-write.json) описывает начальное состояние, участников, порядок операций и ожидаемые эффекты. Вставка второго абзаца испытывает атомарность внутреннего адаптера. Изменение в первой публичной команде `text.replace_exact@1` ограничено точечной заменой. Условные идентификаторы байтов в фикстуре обозначают равенство записанного и воспроизведённого payload. В реальном тесте байты генерирует Yjs, а сравнение проверяет хеш и реальное содержимое.

| Точка испытания | Доказательство |
| --- | --- |
| Одновременно пришли два A42 | Одна принятая команда, одна квитанция, одна вставка, одна последовательность физических обновлений. Запрос с изменённым намерением отклонён |
| Команда подготовила замену, затем упала на вставке до фиксации | В журнале, живой комнате и другом клиенте отсутствуют оба эффекта A42. Обработчик может продолжить работу по сохранённому намерению |
| Процесс упал после фиксации, до применения в комнате и ответа | `status` возвращает квитанцию. После рестарта воспроизводятся те же байты. Команда A43 ждёт догоняющей комнаты. Клиенты и реконструкция содержат одну вставку |
| Человек уже сохранил «20» в целевом фрагменте | Конфликт предусловия, «20» сохранено, новый абзац отсутствует. При правке реквизитов вне цели и неизменном исходном фрагменте обе правки остаются |
| Доступ отозван до фиксации или выдачи статуса | До фиксации новое изменение отклонено. После неё квитанция остаётся в журнале, но результат/фрагмент не выдаётся утратившему доступ субъекту |
| Восстановлена ревизия или сменился владелец комнаты | Старое поколение или номер владения не может записать подготовленное обновление. Проверяются запоздалое outbox-событие и обрыв во время смены владельца |
| Офлайн-клиент прислал старый конкурентный ввод в текущем поколении после A42 | Историческое `at_commit` показывает фактически сохранённую A42. `current` показывает результат слияния, который может потребовать проверки человеком. Эти ответы датированы разными позициями |

Сначала доказываем одиночную семантическую замену с проверкой прав, затем включаем живой адаптер в закрытом тестовом контуре с двумя браузерами и PostgreSQL. При невозможности пропустить обычный sync или Redis-доставку через общую границу порядка строгая команда для живой комнаты остаётся недоступной в профиле. В Hocuspocus 4.3.0 обычный sync удерживается режимом только для чтения, а штатное Redis-расширение применяет сообщения без соединения и hook. Строгий профиль с ним не заявляется. [Стенд A42 с kill процесса](../checks/collaboration/live-write.sh) Можно обслуживать одиночный документ или готовить предложение для ручного решения. Включение живого режима требует зафиксировать задержку обычного ввода и цену восстановления на тех же данных. Целевое значение устанавливает продукт после базовых замеров.
